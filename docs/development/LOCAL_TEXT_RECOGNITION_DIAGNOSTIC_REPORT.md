# 本地文本识别诊断报告 LOCAL_TEXT_RECOGNITION_DIAGNOSTIC_REPORT

> 日期：2026-07-07
> 范围：本地模式（LocalText）识别稳定性专项。**不含真实票据敏感信息**，用样例编号 + 字段命中描述。
> 样例：`/sample` 下 5 份真实脱敏滴滴“合并 PDF”（用户反馈 6 封中 3 封正确；本机现有 5 份，均同版式）。

## 1. 根因（已定位，非盲改正则）

用 PdfPig 词坐标检查行程单表格后确认：

1. **行程单表格按 X 坐标是干净分列的**（序号/车型/上车时间/城市/起点/终点/里程/金额/备注），每个单元格通常是一个独立的 PdfPig 词。
2. 但旧实现用 `page.Text` 把整页文字**按阅读顺序拼成一长串**，再用正则 `SplitStartEnd` 反向切分起点/终点。该正则依赖“终点以 `XX区|` 开头”这一强假设。
3. 失败模式（导致 3/6 正确）：
   - **终点不含 `区|` 结构**（如 `通航机场站地铁站A1口`）→ 切分失败，终点丢失。
   - **地址过长换行**：起点/终点各被拆成两行的多个词（如 `…西`+`门`），拼接串更乱。
   - **车型别名未覆盖**（`滴滴特快` 不在识别列表）→ 混入起点。
   - **列 X 位置每份不同**（表格按内容自适应宽度）→ 无法硬编码 X。
4. 命名核心字段 `{出发地点}`/`{到达地点}` 直接依赖起点/终点，故起终点失败即命名错误。

## 2. 修复措施

1. **坐标行重建**：新增 `PdfTextLine` / `PdfTextLayoutExtractor`，`PdfTextExtractor` 用 `page.GetWords()` 坐标把词按 Y 聚类成行、行内按 X 排序，结果存入 `PdfTextExtractResult.Lines`。
2. **按列取单元格**：`LocalTextInvoiceRecognizer.ParseTripTableByLayout` 定位表头行（含“起点/终点”），读取各列 X（每份自适应），把数据词按**最近列中心**归入起点/终点，并用**列区间过滤**排除车型/城市/时间/里程/金额/备注列。
3. **换行拼接**：同列跨行的多个词按 Y→X 顺序拼接为完整地址。
4. **文本归一化**：新增 `LocalTextNormalizer`（全角转半角、冒号统一、空格折叠、换行统一、金额符号统一、多格式日期规整）。
5. **命名核心字段判定 + OCR 回退**：`KeyFieldEvaluator.IsNamingSufficient` 检查 乘车日期/金额/出发地点/到达地点；本地不足时返回部分成功，`RecognitionPipeline` 据此回退在线 OCR。
6. 正则法保留为 fallback（坐标行不可用时）。

## 4. 仍建议在线 OCR 兜底的情形

1. **图片型/扫描件 PDF**（无文本层）——本地必然失败，走 OCR。
2. 版式与滴滴行程单差异较大、无“起点/终点”表头的行程单。
3. 本地取不到起点或终点时（`IsNamingSufficient=false`）自动回退 OCR；OCR 的 `PassengOrigin/PassengDestination` 起终点更干净。
4. 城市/车型等次要字段本地可能仍有小瑕疵（如样例5 城市取到“市”），不影响命名，可由 OCR 校正。

## 5. 复现方法

```
tools\OfflineTester\bin\Debug\OfflineTester.exe sample --local-only            # 看 5 份本地识别与命名
tools\OfflineTester\bin\Debug\OfflineTester.exe sample --local-only --dump-local-debug   # 生成逐份诊断到 local-debug\
```
诊断文件含：原始文本、归一化文本、坐标行、字段结果、命名结果、缺失字段、是否需 OCR。
**`local-debug\` 含票据信息、已被 `.gitignore` 忽略，切勿提交。**

## 6. 结论
本地不稳定的根因是“全文拼接 + 强假设正则”，已改为“坐标按列取单元格 + 列区间过滤 + 换行拼接 + 归一化”，5 份样例命名核心字段 100% 命中。异常/图片型仍由在线 OCR 兜底。
